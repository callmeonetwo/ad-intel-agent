1. **Virlo нельзя использовать как основу вашей платформы.** Их Terms of Service (редакция от 20.05.2026, §5) запрещают «использовать API, чтобы построить продукт, конкурирующий с Virlo» и «перепродавать сырой доступ к API». Ваша платформа и есть такой продукт. Virlo подходит только как инструмент для сравнения и проверки качества ✅.
2. **Готовой open-source платформы массового анализа вирусных роликов я не нашёл.** Нашёл хорошие *детали* (скачивание, транскрипция, поиск смены кадров), но не целую систему ✅. Поиск был ограничен: доступ к GitHub в этой сессии закрыт для сторонних репозиториев, кроме поиска по метаданным.
3. **Алгоритм «выброса» у Virlo простой, вы его уже реализовали.** Virlo считает `outlier_score = просмотры ÷ медиана просмотров автора` по его последним ≤100 роликам ✅. В вашем `ad_intel/score.py` это поле `views_vs_median`. Это не секрет и не преимущество, преимущество будет в качестве данных и анализа.
4. **Сбор метаданных дешёвый, дорогим будет анализ.** 1 млн роликов собрать стоит примерно **$1 300–3 400** по ценам Apify 🧮. Дорогую часть (транскрипция, кадры, нейросеть) нужно делать только для 1–5% отобранных роликов.
5. **Рекомендация по MVP:** не строить «платформу на миллионы видео», а продать за деньги узкий отчёт по 1–3 нишам на данных, которые у вас уже собираются. Проверить спрос, потом масштабировать (раздел 7).

## 5. Рекомендуемая архитектура

Принцип: **воронка**, каждый следующий этап дороже и применяется к меньшей части данных.

```
Этап 1. Обнаружение (дёшево, 100% роликов)
  списки авторов + хэштеги + поиск по ключевым словам  →  Apify / провайдер данных
  сохраняем: id, ссылка, автор, подписчики, дата, просмотры, лайки, комментарии, длительность, звук, подпись

Этап 2. Нормализация и дедупликация (почти бесплатно)
  один ролик = один video_id на платформе; копии ловим по хэшу аудио или превью (pHash)

Этап 3. Скоринг выбросов (почти бесплатно, SQL)
  views_vs_median по автору, с поправкой на возраст ролика и размер аккаунта

Этап 4. Глубокий анализ (дорого, только 1–5% лучших)
  скачать ролик (yt-dlp) → faster-whisper (речь) → PySceneDetect (склейки)
  → 6–10 кадров + текст на экране → Claude vision: хук, формат, CTA → JSON

Этап 5. Закономерности (SQL + статистика, без нейросети)
  частота признаков у выбросов против контрольной группы того же размера и ниши

Этап 6. Отчёт и рекомендации (Claude получает только посчитанные числа)
```

### Стек (простой и достаточный для старта)

| Задача | Выбор | Почему |
|---|---|---|
| Метаданные и временные ряды | **PostgreSQL** (таблица снимков `video_snapshots`, партиции по месяцам) | Хватает до сотен миллионов строк, не нужна отдельная система |

## 6. Методика выбросов и закономерностей

### Простыми словами: термины
- **Медиана** — число «посередине»: половина роликов набрала больше, половина меньше. Не боится одного супер-хита, в отличие от среднего.
- **Выброс (outlier)** — ролик, набравший заметно больше обычного для этого автора.
- **Перцентиль** — «обогнал N% своих роликов». 89-й перцентиль = лучше 89% роликов автора.
- **MAD** — типичное отклонение от медианы, устойчивое к хитам. Нужно, чтобы не считать выбросом то, что для автора норма.
- **Lift (подъём)** — во сколько раз признак чаще встречается у выбросов, чем у обычных. Пример: хук-вопрос в 40% выбросов и в 20% обычных роликов, lift = 2.0.

### Рекомендуемый расчёт
1. Для каждого автора берём его последние **N ≥ 10** роликов (лучше 30–100) и считаем медиану просмотров.
2. `outlier = log(просмотры) − log(медиана автора)`. Логарифм нужен, потому что просмотры растут не линейно, а в разы.
3. **Поправка на возраст:** сравниваем не итоговые просмотры, а просмотры за фиксированный срок (например, 7 дней). Для этого нужны снимки во времени. Пока их нет, помечайте ролики моложе 3 дней как «ещё рано».
4. **Поправка на нишу и размер:** сравнивать автора ещё и с авторами того же размера и ниши (корзины по подписчикам: <10 тыс., 10–100 тыс., 100 тыс.–1 млн, >1 млн).
5. **Доверие:** если у автора меньше 10 роликов, показывать «мало данных» и не ставить метку.

Вы можете сразу сверить свою формулу с Virlo: возьмите 20 роликов, прогоните через их проверку ($0.50 × 20 = $10), сравните метки `viral/mega_viral` с вашими. Их границы: `mega_viral` ≥ 10, `viral` от 3 до 10, `above_average` от 1,5 до 3 ✅.

### Как искать закономерности и не обмануть себя
- Сравнивайте выбросы с **контрольной группой из тех же авторов и ниши**, иначе «закономерность» может быть просто особенностью ниши.
- Для каждого признака показывайте **размер выборки и доверительный интервал** (диапазон, в котором, скорее всего, лежит настоящее значение).
- При проверке сотен признаков часть «значимых» окажется случайными. Применять поправку (FDR, контроль доли ложных открытий).
- В интерфейсе писать «чаще встречается у успешных роликов», а не «приводит к успеху». Корреляция не равна причине.
- **Прогноз вирусности** отложить до накопления данных; первая версия показывает только «доля выбросов по формату с интервалом», а не «этот ролик наберёт X».

### Проверка качества автоматического разбора хуков
Возьмите 50 роликов, разметьте хуки вручную (вы или нанятый человек, ~2 часа), сравните с разметкой Claude. Критерий: согласие по типу хука не ниже 80%. Если ниже, улучшать промпт, а не масштабировать.

## 7. MVP и проверка спроса

### Рекомендуемый MVP: «отчёт по нише с выбросами» (2–3 недели)

**Что строим (всё на существующем коде):**
1. Добавить в `collect.py` TikTok и YouTube Shorts (два Apify-скрапера из раздела 3).
2. Заменить файлы `data/raw/*.jsonl` на SQLite или Postgres (одна таблица `videos`, одна `snapshots`).
3. Реализовать скоринг выбросов из раздела 6 (поверх `views_vs_median`).
4. Для топ-5% выбросов добавить глубокий разбор: faster-whisper + PySceneDetect + 6 кадров в Claude vision.
5. Выдавать отчёт HTML/PDF по одной нише.

**Что не строим в MVP:** личные кабинеты, оплату, white-label, прогнозы, миллионы роликов. Достаточно 5–20 тысяч роликов на нишу.

### Проверка спроса до разработки платформы (0 строк кода)
1. Выберите 1 нишу, в которой вы уже разбираетесь (например, AI-видео и реклама, она есть в вашем `niches.json`).
2. Сделайте **один отчёт по существующему прототипу** (вы уже умеете, $0.13 на запуск).
3. Найдите 20 авторов или небольших агентств в этой нише и отправьте им персональный пример: «вот 3 ролика-выброса вашей ниши и что их объединяет».
4. Предложите платную версию: **$49 за разовый отчёт или $99/мес за еженедельный**. Ориентир: Virlo берёт $49–199/мес ✅.
5. **Критерий успеха:** 3 из 20 согласились платить или внесли предоплату. Меньше этого, значит нужно менять нишу или предложение, а не писать платформу.

### Порядок работ

| Шаг | Срок | Результат |
|---|---|---|
| 1. Тест скраперов на 1 нише: 3 платформы, по 1 000 роликов | 2–3 дня | Реальная стоимость и доля пропусков |
| 2. Ручная проверка 50 разборов хуков | 1 день | Процент согласия, решение о качестве |

### Как выполнить шаг 1 (пошагово, без кода)
1. Откройте [apify.com](https://apify.com) и войдите в аккаунт (ваш токен уже в `.env`).
2. Нажмите **Store** (магазин) и введите в поиск `TikTok Scraper`, выберите `clockworks/tiktok-scraper`.
3. На странице нажмите **Try for free** (попробовать бесплатно).
4. В поле `hashtags` введите хэштег вашей ниши (например, `aiart`), в `resultsPerPage` введите `100`.
5. Нажмите **Start**. **Ожидаемый результат:** через 1–3 минуты вкладка **Output** покажет таблицу из 100 строк с просмотрами, лайками, автором, датой, ссылкой.
6. Проверьте столбец стоимости в разделе **Usage**. **Ожидаемое:** около $0.37–0.50 за 100 роликов.
7. Повторите для `apify/instagram-reel-scraper` и `streamers/youtube-shorts-scraper`.
8. Сохраните результаты в таблицу и посчитайте, у скольких строк не хватает просмотров или даты (это «доля пропусков»).

## 8. Риски и открытые вопросы

| Риск | Что делать |
|---|---|
| Скраперы сообщества внезапно ломаются | Хранить собранные данные у себя, абстрагировать сбор за интерфейсом `Collector`, держать 2 поставщика на платформу |
| Условия платформ (TikTok, Meta, YouTube) запрещают автоматический сбор | Юрист до продаж; использовать только публичные данные без входа; письменная политика удаления |
| Копирование видео (авторское право) | Не хранить и не показывать исходные видео, хранить кадры и производные признаки только для отобранных; показывать ссылки на оригинал |
| Просмотры ≠ эффективность | Всегда считать относительно автора, возраста, ниши; для рекламы не смешивать «просмотры Reels» и «дни показа рекламы» (разные сигналы) |
| Нельзя обещать прогноз | Только «доля выбросов по формату + интервал + размер выборки» |
| Зависимость от Virlo | Не использовать их данные в продукте без письменного разрешения (раздел 2) |
